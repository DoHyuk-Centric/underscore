# 밑줄 — 백엔드 선택

## 결론

밑줄 백엔드는 **NestJS**로 구성하고, HTTP 요청을 받는 엔진은 **Fastify 어댑터**를 사용한다.

초기 배포는 하나의 EC2에서 동작하는 **모듈형 모놀리스**다. 기능은 모듈로 분리하되, 주문·시세·인증을 처음부터 여러 서버로 나누지 않는다.

## NestJS를 선택한 이유

NestJS가 유일한 선택지는 아니다. 순수 Fastify만으로도 밑줄을 만들 수 있다. 그러나 밑줄 백엔드에는 인증, 가상 주문, 시세 수집, SSE 전달, 공시 수집, AI 리뷰처럼 성격이 다른 기능이 함께 존재한다. NestJS의 모듈·의존성 주입·가드·예외 처리 구조는 이 기능들이 커져도 책임을 분명하게 유지하는 데 적합하다.

| 밑줄의 요구 | NestJS로 얻는 것 |
| --- | --- |
| 토스 로그인과 밑줄 세션 | 인증 가드와 모듈 경계 |
| 가상 매수·매도의 정확한 처리 | 거래 서비스를 한곳에 모으고 테스트 가능한 구조 |
| 토스 시세 수집과 가격 전달 | 장기 실행 작업과 SSE 엔드포인트의 분리 |
| 공시·AI 리뷰 같은 후속 작업 | 작업별 모듈과 명확한 의존성 |
| 향후 채팅·프레즌스 | 웹소켓 게이트웨이 확장 경로 |

## Fastify의 역할

NestJS는 백엔드의 구조와 기능을 담당한다. Fastify는 EC2에서 외부 HTTP 요청을 실제로 받는 저수준 웹 엔진이다.

```text
앱인토스 FE
  → POST /orders
  → Fastify가 HTTP 요청 수신
  → NestJS OrdersController
  → TradingModule
  → PostgreSQL
  → 체결 결과 응답
```

NestJS는 기본적으로 Express를 HTTP 엔진으로 사용하지만, Fastify 어댑터를 공식 지원한다. 밑줄은 빠른 주문 응답과 SSE 연결을 다루므로 Fastify를 사용한다. Fastify 선택은 NestJS의 Controller·Service·Module 구조를 바꾸지 않는다.

Fastify는 앱에서 들어오는 요청을 받는 역할이다. 백엔드가 토스증권 REST API에 시세를 요청할 때는 별도의 서버 엔진이 아니라 서버 측 `fetch`를 사용한다.

## 백엔드 모듈

| 모듈 | 책임 |
| --- | --- |
| `AuthModule` | 앱인토스 로그인 인가 코드 교환, 밑줄 세션 발급·검증 |
| `TradingModule` | 가상 매수·매도, 잔액·lot·주문 트랜잭션, 중복 주문 방지 |
| `PortfolioModule` | 보유 종목, lot, 평가손익, 거래 기록 조회 |
| `MarketDataModule` | 토스증권 웹소켓·REST 호출, 액세스 토큰, 가격 캐시, 구독 관리 |
| `PriceStreamModule` | SSE로 사용자에게 최신 가격·평가손익 전달 |
| `DisclosureModule` | DART 공시 수집과 정규화 |
| `ReviewModule` | lot 전량 소진 후 AI 거래 리뷰 생성·저장. 주문 경로와 분리 |

## 가상 매수·매도 처리

밑줄은 모의투자 서비스다. 매수·매도 버튼을 누를 때 토스증권 주문 API를 호출하지 않는다. 토스증권은 시세를 수집하는 용도로만 사용하고, 가상 체결은 밑줄 서버와 PostgreSQL이 확정한다.

```text
POST /orders
  → 밑줄 세션 확인
  → 잔액·보유 lot과 최신 가격 캐시 조회
  → PostgreSQL 트랜잭션에서 잔액·lot 최종 재확인
  → 주문 기록·lot·잔액을 함께 확정
  → 체결 결과 반환
  → SSE로 보유 상태와 평가손익 갱신
```

잔액과 보유 lot의 초기 조회는 가격 캐시와 병렬로 할 수 있다. 그러나 최종 확정은 반드시 DB 트랜잭션에서 다시 검증한다. 여러 주문이 동시에 들어와도 잔액이 중복 사용되지 않도록 하기 위함이다.

주문 요청에는 `clientOrderId`를 포함한다. PostgreSQL의 고유 제약으로 같은 요청을 두 번 처리하지 않는다.

## 시세 처리와 실시간 전달

토스증권 웹소켓은 밑줄 서버가 외부 서비스에 연결하는 통로다. 체결·호가가 필요한 종목은 서버가 토스 웹소켓으로 구독한다. 토스 웹소켓의 구독 한도를 넘는 보유 종목은 REST 현재가 다건 조회로 보완한다.

```text
토스증권 웹소켓 또는 REST
  → MarketDataModule의 가격 캐시
  → PriceStreamModule의 SSE
  → 앱인토스 FE
```

SSE는 현재가·평가손익처럼 서버에서 사용자에게 보내기만 하는 데이터를 전달한다. 사용자 간 채팅, 프레즌스, 공동 편집처럼 양방향 실시간 통신이 필요해지면 밑줄 자체 웹소켓을 추가한다.

## 초기 인프라 경계

| 역할 | 초기 선택 |
| --- | --- |
| 애플리케이션 서버 | AWS EC2의 NestJS + Fastify |
| 거래 원장 | PostgreSQL + Drizzle ORM |
| 시세 캐시 | 백엔드 프로세스 메모리 |
| 실시간 전달 | SSE |
| Redis | 다중 EC2, 공용 캐시, Pub/Sub이 필요할 때 추가 |

토스증권 API의 허용 IP 정책 때문에 EC2의 고정 외부 호출 IP를 등록한다. 토스증권 API 키와 `client_secret`은 서버의 비밀 환경 설정으로만 보관하며 FE에 전달하지 않는다.

## 성능 기준

주문 경로에서는 토스증권 API, AI 호출, 공시 수집처럼 지연되거나 실패할 수 있는 외부 작업을 기다리지 않는다. 가격 캐시와 짧은 PostgreSQL 트랜잭션만 사용한다.

- 버튼 터치 직후: FE가 즉시 처리 중 상태 표시
- 일반적인 체결 확정: 100~150ms 목표
- 95% 체결 확정: 250ms 이내 목표
- 300ms 초과: 측정·개선이 필요한 구간

## 대안과 결정 범위

순수 Fastify는 더 적은 추상화와 높은 원시 HTTP 성능이 필요할 때 적합하다. 하지만 현재 밑줄은 성능만큼 인증·거래 정합성·시세·후속 작업의 구조적 분리가 중요하다. 따라서 NestJS + Fastify를 기본으로 선택한다.

이 결정은 구현 구조의 기준이며, 실제 부하 테스트에서 주문 경로가 목표를 충족하지 못할 때 Fastify 네이티브 경로 또는 모듈 분리를 검토한다.
