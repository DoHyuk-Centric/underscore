# 밑줄 — 아키텍처

## 플랫폼 — 앱인토스 WebView

앱인토스는 WebView와 React Native(Granite) 두 경로를 제공한다. **WebView 선택.**

**이유**

- 차트. TradingView Lightweight Charts는 웹 라이브러리라 RN에서 그대로 못 쓴다. RN으로 가면 차트만 웹뷰로 끼우는 하이브리드가 되므로 처음부터 WebView가 낫다
- 같은 코드가 웹 URL로도 열린다 → **심사가 늦어져도 포트폴리오 링크는 살아 있다**
- 웹 개발 경험을 그대로 활용, 빠른 업데이트 사이클

**감수하는 것**

- 백그라운드 전환 시 연결 끊김 → 재연결 + 스냅샷 재동기화 필요
- 토스 네이티브 UI와 이질감. 심사에서 불리할 수 있음

**푸시는 지원된다** (앱인토스 FAQ·릴리즈 노트 확인). 후속 리뷰를 제외한 것은 기술적 제약 때문이 아니라 제품 판단이다.

## 서버가 반드시 필요한 이유

두 가지 독립된 이유가 있다. 하나만으로도 서버는 확정이다.

### ① client_secret 보호

`client_secret`을 웹뷰 클라이언트에 넣으면 개발자도구로 노출된다. 그리고 그 크레덴셜은 **실제 증권 계좌의 주문 권한까지 포함한다** — 조회가 되면 주문도 된다. IP 정책과 무관하게 클라이언트 직접 호출은 불가능하다.

### ② 허용 IP 정책

토스증권 WTS 설정 > Open API > **허용 IP 관리**에 호출할 IP를 등록해야 하며, 등록되지 않은 IP에서의 호출은 키가 맞아도 **403으로 차단**된다. REST와 웹소켓에 동일한 목록이 적용된다.

→ 서버는 **고정 IP**를 가져야 한다. Vercel 서버리스는 egress IP가 유동적이라 부적합. Fly.io / Railway / EC2 등 고정 IP 확보가 가능한 곳.

### 모바일에서 IP 고정은 원리적으로 불가

| 경로 | 이유 |
| --- | --- |
| 셀룰러(LTE/5G) | 통신사 CGNAT. 다수 가입자가 소수 공인 IP를 공유하고 통신사가 임의 배정. 이동만으로도 바뀐다. 사용자가 통제할 수단 자체가 없음 |
| Wi-Fi | ISP가 DHCP로 동적 할당. 공유기 재부팅·리스 갱신 시 변경. 고정 IP는 ISP 유료 상품 |

"사용자 폰 IP를 허용목록에 등록"은 성립하지 않는다. 토스 API의 제약이 아니라 모바일 네트워크의 구조다.

## 크레덴셜 전략 — 플랜 A / B / C — **A·B 폐기 확정**

토스증권 공식 회신: "개인투자목적으로 본인께서 이용하시는 것이 아닌, 제3자 제공은 모두 불가." 근거와 조사 상세는 [04-constraints.md](04-constraints.md) 참고.

| 방식 | 상태 | 내용 |
| --- | --- | --- |
| **A** | **폐기** | 운영자 크레덴셜로 모든 사용자에게 재배포 → 제3자 제공에 정면 해당 |
| **B** | **폐기** | 사용자가 자기 키를 발급받아 우리 서버에 등록, 서버가 대신 호출 → 계정 소유자 본인이 아니라 서버(제3자)가 이용하는 구조라 마찬가지로 제3자 제공. 보안·규제 리스크(마이데이터 스크래핑 금지와 동일 패턴)도 별도로 있음 |
| **C** | 1차 MVP 이후 검토 | 시세 소스 교체 — 조사 결과 국내(코스콤/KRX)는 법인만, 공공데이터는 상업이용 금지+하루 지연, 해외 벤더(Twelve Data)는 월 $1,099~. 개인 프로젝트 규모에서 즉시 쓸 수 있는 대안 없음 |

### 플랜 B가 폐기된 이유 (기록용)

**동작은 한다.** IP는 우리 서버 하나로 고정되므로, 사용자가 자기 WTS에서 우리 서버 IP를 허용목록에 등록하면 된다.

**그러나 두 가지 이유로 폐기했다.**

1. **약관**: "본인이 이용하시는 것"만 허용되므로, 사용자의 키를 서버가 대리 호출하는 구조는 여전히 제3자 제공에 해당한다.
2. **보안/UX**: 사용자 동선(PC WTS 로그인 → 키 발급 → 서버 IP 등록 → 앱에 secret 입력)이 "진입장벽 0" 포지셔닝과 정면 충돌하고, `client_secret`이 실계좌 주문 권한을 포함해 유출 시 개인 프로젝트가 감당할 수 없는 책임이 발생한다. 이 패턴은 2020년 신용정보법 개정으로 금지된 "스크래핑 방식 마이데이터"와 구조적으로 동일하다.

### 1차 MVP의 결론

**앱인토스 배포는 지금 진행한다.** TDS도 정식으로 쓴다. 다만 매수/매도 체결에 필요한 시세는 토스 API로 조회하지 않고 **사용자가 직접 입력**하는 방식으로 대체해 제3자 제공 문제 자체가 발생하지 않게 한다. 핵심 기능은 AI 솔루션(판단 리플레이)이고, 정교한 시세 연동(실시간·지연시세 등)은 이후 과제로 미룬다.

## 실시간 시세 전송 — **미결정**

### 결정 시점

**화면 7개와 기능 명세가 확정된 직후.** 지금은 기능이 다 나오지 않아 전송 방식을 못박는 것은 순서가 틀렸다.

### 판단 기준

> 초 단위 미만 반응성이 필요한 화면이 하나라도 있는가?

이 결정을 뒤집을 수 있는 미확정 기능: 호가창 노출 여부, 공시 카드 실시간 등장, 조건 감시(목표가 도달 알림).

### 후보 1 — REST 폴링 + 서버 캐시 + SSE

```rust
서버(고정 IP) --1초-- 토스 /prices 배치 조회 --> 메모리 캐시 --SSE--> 클라이언트
```

- Rate limit: `MARKET_DATA` **초당 15회**, `MARKET_DATA_CHART` 초당 20회. `client_id` 단위 예산이므로 **사용자 수와 무관**하고 종목 수에만 비례
- 서버가 초당 1~2회만 써도 충분

### 후보 2 — 웹소켓 (`wss://openapi-ws.tossinvest.com/ws/v1`)

따라오는 제약:

| 제약 | 내용 |
| --- | --- |
| 동시 연결 | **계정당 2개.** 초과 시 가장 오래된 연결이 종료됨 → 사용자별 연결 불가, 서버 1연결 fan-out 강제. 배포 중 구·신버전 겹치면 끊김 |
| 구독 선언 | full-replace. 서버가 전체 종목 집합을 상태로 들고 재선언해야 함 |
| keepalive | 클라이언트 수신이 180초 없으면 종료. 60초 간격 PING 권장 |
| 시세 채널 | LOSSY — 밀리면 프레임 유실, sequence 미제공 |
| 연결당 구독 | 100건 |

### 확인 필요

- `GET /api/v1/prices`가 **여러 종목 배치 조회**를 지원하는지. 안 되면 종목 1개당 1호출이라 초당 15종목이 상한

## 구현 주의사항

- 웹뷰 백그라운드 전환 시 연결 끊김 → 재연결 로직 + 복귀 시 스냅샷 재동기화
- 매 틱마다 리렌더하면 성능 저하 → 시세는 별도 store/ref에 쌓고 `requestAnimationFrame` 또는 짧은 인터벌(200~300ms)로 화면만 갱신

## 시연 관련 메모

장 마감 시간에는 거래가 불가능하다. 이는 실제 시장이 그런 것이므로 **제품 문제가 아니다.** 포트폴리오 발표는 시연 영상으로 해결한다. 과거 시세 재생 "데모 모드"는 스코프 아웃.
