# 밑줄 — 급등 종목 AI 진단 회고

이 문서는 [AI-진단-개선-로그.md](./AI-진단-개선-로그.md)와 역할이 다르다. 개선 로그는 "무엇이 얼마나 좋아졌는지"를 버전별 수치로 남긴다. 이 문서는 **왜 그렇게 만들었는지, 어떤 걸 착각했다가 고쳤는지, 다음에 프롬프트나 코드를 고칠 때 뭘 참고하면 되는지**를 남긴다. 새로 프롬프트를 쓰거나 파이프라인을 바꿀 사람이, 이미 시도해서 실패했거나 이미 판단해서 정한 것을 다시 반복하지 않도록 하는 게 목적이다.

## 왜 이 구조로 만들었는가

### 1. AI가 직접 검색하지 않고, 뉴스 API + 텍스트 생성으로 나눈 이유

처음엔 Gemini의 Google 검색 그라운딩을 쓰려고 했다. AI가 알아서 찾아 정리하는 그림이 가장 자연스럽기 때문이다. 그런데 무료 API 키로는 검색 그라운딩 자체가 429(할당량 초과)로 막혀 있었고, 이건 결제 계정을 등록해야 풀리는 문제였다(검색 없이 텍스트만 생성하는 건 무료로 됐다).

여기서 판단한 것: "AI가 직접 검색"은 어느 회사(OpenAI·Anthropic·Google) 제품이든 검색 자체에 실비용이 들어서 유료다. 반면 **뉴스 API로 사실을 모으고, AI에게는 그 사실을 텍스트로 정리시키는 것**은 검색 비용이 없다. 두 방식의 결과물 차이(AI가 스스로 고른 검색어로 찾는 것 vs 고정된 검색어로 미리 찾아준 것 중에서 AI가 고르는 것)는 실제로는 크지 않다고 보고, 비용 0원인 후자를 택했다. 이 판단은 [docs/AI.md](./AI.md)의 "AI에는 백엔드가 이미 수집·계산·출처화한 context를 전달하고, AI가 임의로 외부 데이터를 찾게 하지 않는다"는 원칙과도 맞았다.

**다음에 참고할 점**: 검색 그라운딩을 쓸지 다시 검토한다면, 결제 계정 등록 자체는 이 규모(하루 10종목)에서 거의 0원이라는 걸 이미 확인해뒀다([개선 로그의 운영 메모](./AI-진단-개선-로그.md#운영-메모) 참고). "돈이 드니까 안 쓴다"가 아니라 "지금 방식으로 충분한 품질이 나온다"가 실제 이유다.

### 2. 뉴스와 공시를 분리된 ID 공간(`newsIds` / `disclosureIds`)으로 넘긴 이유

처음엔 뉴스만 있었다. DART 공시를 추가하면서 하나의 `newsIds` 배열에 같이 넣을지, 분리할지 고민했다. 분리한 이유는 두 가지다.

1. 화면에서 "[공시]"로 시작하는 **뉴스 기사 제목**과 진짜 DART 공시 링크가 헷갈리는 문제가 있었다(예: 파이온엑스 진단의 근거 중 "[공시] 국영지앤엠·서울반도체 '공매도 금지'…"는 뉴스 기사 제목이지 DART 공시가 아니다). ID 공간을 분리하면 화면에서 `DART` / `뉴스` 배지를 정확히 붙일 수 있다.
2. 프롬프트에서 "공시를 뉴스보다 우선한다"는 규칙을 주려면, 모델이 두 자료를 구분해서 인식해야 규칙을 지키기 쉽다. 하나로 섞으면 모델이 어느 게 공시이고 어느 게 뉴스인지 텍스트로 다시 판단해야 한다.

**다음에 참고할 점**: 이 분리는 아직 완전히 해결되지 않았다. "[공시]"로 시작하는 **뉴스 제목** 자체는 여전히 헷갈릴 수 있다(사람이 읽을 때). 근본적으로는 뉴스 소스 표시와 공시 소스 표시를 UI에서 완전히 분리하거나, 뉴스 제목의 "[공시]" 접두어를 표시에서 지우는 게 나을 수 있다.

### 3. DART 공시 조회 기간을 기준일 -3일 ~ +3일로 잡은 이유와, 그게 여전히 부족한 이유

처음엔 기준일 당일만 봤다. 그런데 실제 데이터를 보니 **조회공시 요구에 대한 답변**은 요구일로부터 며칠 뒤에 나온다는 걸 발견했다(SH에너지화학: 9/23 조회공시 요구 → 답변 기한 9/28). 그래서 +3일을 추가했다.

그런데 목표 데이터를 직접 조사하면서, **-3일로도 부족한 경우**를 여러 개 발견했다.
- 파이온엑스의 유상증자 공시는 9/17(기준일 9/23 기준 -6일)이었다.
- 아스플로의 공급계약·설비투자 공시는 8/25, 9/8(기준일 기준 -29일, -15일)이었다.
- SH에너지화학의 가처분 신청 공시는 9/11(기준일 기준 -12일)이었다.

**판단**: 급등의 배경이 되는 공시는 "그 주"에만 나오는 게 아니라, **몇 주 전에 나온 뒤 뉴스가 뒤늦게 그걸 재조명하면서 주가가 움직이는 경우**가 많다. 그래서 개선 로그의 "다음 후보"에 "기준일 전후 공시 + 최근 30일 주요 공시(유상증자·전환사채·공급계약·가처분·관리종목·조회공시·상호변경)"를 별도로 추가하자고 적어뒀다. 짧은 기간의 "당일 근거"와 긴 기간의 "배경 맥락"은 서로 다른 조회라 나눠서 설계해야 한다는 게 이번에 얻은 결론이다.

### 4. 정형 공시를 걸러내는 필터를 만들었다가, 그게 정보를 지워버렸다는 걸 깨달은 과정

[dart.client.ts](../apps/api/src/stock-diagnosis/dart.client.ts)의 `NOISE_REPORT_PATTERN`(소유상황보고서, 거래계획보고서, 기업설명회, 자기주식취득결과보고서)은 "급등 배경과 거리가 먼 정형 공시"를 거르려고 처음부터 넣어둔 필터다. 판단 근거는 "이런 공시는 매달 정기적으로 올라오는 사무적인 공시라 급등 이유가 되기 어렵다"였다.

그런데 목표 데이터를 조사하다가, **토마토시스템 임원의 소유상황보고서**(9/22 제출)에 "급등 기간(9/18~22) 동안 보유주식 6만 3,034주를 장내 매도했다"는 내용이 있는 걸 발견했다. 이건 "급등 이유"는 아니지만, **투자자가 확인해야 할 주의사항**으로는 중요한 사실이었다. 필터가 "이유가 될 수 없는 공시"와 "주의사항이 될 수 있는 공시"를 구분하지 못하고 통째로 걸러버린 것이다.

**다음에 참고할 점**: 이건 필터를 없애야 한다는 뜻이 아니다. `headline`(급등 이유)을 위한 조회와 `caution`(주의사항)을 위한 조회는 원래 다른 목적인데 같은 공시 목록을 재사용하고 있었던 게 문제다. 개선 로그의 "다음 후보"에 "소유상황보고서는 버리지 말고, 조회 기간의 임원·주요주주 장내매도만 요약해 입력"을 별도 항목으로 추가했다.

### 5. 모델 폴백 순서(`gemini-3.5-flash` → `gemini-3.5-flash-lite`)를 정한 근거

처음엔 `gemini-2.5-flash`를 쓰려 했으나 신규 사용자에게 404로 막혀 있었다. 그다음 시도한 `gemini-3.7-flash`, `gemini-3.6-flash`는 실시간 테스트에서 503(과부하)이 잦았다. `gemini-3.5-flash-lite`만 안정적으로 응답했다.

처음엔 `flash-lite`를 기본값으로 고정했는데, 실제로 돌려보니 **문장 품질이 `flash`보다 떨어진다**는 걸 확인했다(v1 결과에서 "보조 보도되었습니다" 같은 어색한 문장). 그래서 "품질 좋은 걸 먼저 시도하고, 안 되면 안정적인 걸로 넘어간다"는 폴백 체인으로 바꿨다([gemini.client.ts](../apps/api/src/stock-diagnosis/gemini.client.ts)의 `resolveGeminiModels`). 이 판단은 "무조건 안정적인 모델만 쓴다"와 "무조건 품질 좋은 모델만 쓴다" 둘 다를 포기하고, **실패하면 자동으로 물러나는 구조**를 택한 것이다.

**다음에 참고할 점**: `gemini-3.5-flash`의 실제 무료 일일 한도는 문서(1,500 RPD로 알려짐)와 다르게 **약 20회**로 관찰됐다. 이건 관찰 시점의 상황일 수 있어 고정된 사실로 단정하면 안 된다. 공식 문서와 실제 동작이 다르면 **실제 동작을 믿어야 한다** — 이건 이번 세션에서 두 번 반복된 패턴이다(아래 "실수와 교정" 참고).

작업하면서 실제로 틀렸다가 고친 것들이다. 프롬프트가 AI에게 "지어내지 말라"고 요구하는 것과 똑같은 실수를, 사람(나)도 저질렀다는 걸 남겨둔다.

## 프롬프트를 다시 쓸 때 참고할 점

위 판단·실수에서 실제로 프롬프트 문구에 반영해야 할 것들을 뽑았다. [diagnosis.prompt.ts](../apps/api/src/stock-diagnosis/diagnosis.prompt.ts)를 고칠 때 이 목록을 체크리스트로 쓰면 된다.

1. **"확정된 사실"과 "추진 중인 일"을 분리해서 쓰라고 명시한다.** 레메디의 "NASA 선정"(확정)과 "스페이스X 탑재"(추진 중, 회사도 "현재 계획"이라고만 밝힘)처럼, 같은 기사 안에서도 확정 단계가 다른 사실이 섞여 있다. [docs/AI.md](./AI.md)가 이미 "확인된 사실 / 가능한 해석 / 판단으로 남겨둘 부분"을 구분하라고 하는데, 급등 진단 프롬프트에도 이 구분을 더 명시적으로 넣을 필요가 있다.
2. **금액이 "전체 규모"인지 "이 회사의 몫"인지 구분해서 쓰라고 명시한다.** 쓰리빌리언의 "최대 80억 원"은 쓰리빌리언 혼자 받는 돈이 아니라 KAIST 주관 과제 전체 규모였다. 이런 식의 금액 주체 혼동은 다시 나올 수 있다.
3. **회사의 공식 사업(정기보고서 사업의 개요)과 지금 테마가 다르면, 그 불일치 자체를 주의 사항에 쓰라고 지시한다.** HT로보틱스가 "로봇"으로 개명했지만 정기보고서상 로봇 사업은 아직 "사업목적 추가 단계"였다. 이 자료는 이미 프롬프트 입력에 들어가 있는데(회사정보의 `사업의개요`), 이를 활용하라는 명시적 지시가 없었다.
4. **여러 종목을 나열한 시황 기사를 근거로 쓸 때는, 그 종목에 해당하는 부분만 인용하라고 명시한다.** (이미 "같은 이름의 다른 회사·다른 대상에 대한 기사는 근거로 쓰지 않는다"는 규칙이 있지만, "여러 종목이 섞인 기사에서 해당 종목 부분만 뽑아 쓴다"는 규칙은 없다.)
5. **시가총액·상장폐지 기준선처럼 한국 상장 규정에 관한 숫자는, 모델이 알고 있다고 가정하지 말고 입력으로 직접 줘야 한다.** "시가총액이 관리종목 기준선을 넘었다/못 미친다" 같은 판단은 모델의 사전 지식에 의존하면 안 되고, 서버가 계산해서 넘겨야 한다.

## 프로세스에 대한 메모

- **테스트 코드는 미리 합의하지 않고 계속 늘렸다.** 사용자가 "spec은 뭔데 자꾸 작성합니까?"라고 물었을 때, 목적(비용 없이 회귀 확인)은 정당했지만 **미리 여쭤보지 않고 파일을 계속 늘린 것**은 별도로 짚을 문제였다. 다음에는 새로운 종류의 테스트 파일을 만들기 전에 한 번은 방향을 확인받는 게 낫다.
- **비교 대상(목업 vs 실제 파이프라인 결과)의 기준일이 다르면 비교 자체가 왜곡된다.** 처음 만든 목표 데이터(`target-20260917.json`)는 v1·v2(9/23)와 기준일이 달라서 "같은 종목끼리" 비교가 불가능했다. 그래서 비교 페이지에 "기준일이 다르면 순위로만 짝짓는다"는 폴백을 만들어야 했다. 이후 같은 기준일(9/23)로 직접 조사한 `target-20260923.json`을 추가해서야 종목 단위 비교가 가능해졌다. **버전을 비교할 목적이라면 처음부터 같은 기준일로 맞추는 게 낫다**는 걸 뒤늦게 확인한 셈이다.
- **DB에 실제로 반영하지 않고 "드라이런"으로 결과만 뽑아보는 방식**을 v2에 적용했는데, 이게 유용했다. 코드를 계속 고치는 중에는 DB를 매번 오염시키지 않고 결과만 파일로 남겨서 비교할 수 있었다. 다음 버전(v3 등)을 만들 때도 먼저 드라이런으로 품질을 확인한 뒤에 DB 반영 여부를 정하는 순서를 유지하는 게 좋다.
