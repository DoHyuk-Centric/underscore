# 밑줄 — 프론트엔드 기술 선택

## 결론

밑줄의 앱인토스 미니앱 프론트엔드는 **React + Vite**로 구현한다. 앱인토스 WebView SDK와 **TDS Mobile / TDS Mobile AIT**를 사용하고, 클라이언트 UI 상태는 **Zustand**, 서버 통신은 표준 **`fetch` 기반 API 래퍼**, 경계 데이터 검증은 **Zod**, 실시간 시세 수신은 **SSE**를 기본으로 한다.

| 영역 | 선택 | 상태 |
| --- | --- | --- |
| 프레임워크·빌드 | React + Vite | 확정 |
| 앱 플랫폼 연동 | 앱인토스 WebView SDK | 확정 |
| 디자인 시스템 | TDS Mobile / TDS Mobile AIT | 확정 |
| 클라이언트 UI 상태 | Zustand | 확정 |
| HTTP 통신 | 표준 `fetch` 기반 API 래퍼 | 확정 |
| 런타임 검증·공유 타입 | Zod | 확정 |
| 시세 수신 | SSE | 기본안 |
| 자체 웹소켓 | 채팅·프레즌스 등 양방향 기능이 생길 때 | 보류 |
| Axios | 현 시점 미도입 | 보류 |

## React + Vite를 선택한 이유

밑줄의 핵심 사용 환경은 토스 앱 안의 WebView다. 종목 차트, 시세 수신, 가상 매수·매도, 거래 근거 입력처럼 브라우저에서 계속 상호작용하는 화면이 중심이므로 React의 클라이언트 UI 모델이 잘 맞는다.

Vite는 앱인토스 WebView 미니앱의 정적 빌드 결과물을 만들기에 단순하다. 앱인토스 WebView SDK와 TDS를 React 프로젝트에 붙일 수 있고, EC2의 백엔드와도 독립적으로 배포할 수 있다.

Next.js는 서버 렌더링(SSR), 검색 엔진 노출(SEO), 공개 콘텐츠의 첫 화면 성능에 강점이 있다. 그러나 현재 밑줄의 핵심 유입과 사용처는 앱인토스이며, 로그인·시세·주문은 모두 상호작용 중심이다. 이 이점은 초기 미니앱의 핵심 요구가 아니다.

외부 웹은 초기에는 서비스 소개, 시연, 포트폴리오 목적의 정적 페이지로 제공한다. 웹에서도 가상 매수·매도까지 완전히 지원할 필요가 생기면 앱인토스 전용 로그인과 분리된 웹 인증을 설계하고, 그 시점에 Next.js 도입을 다시 판단한다.

## TDS와 앱인토스 WebView SDK

TDS Mobile / TDS Mobile AIT는 버튼, 입력, 리스트, 바텀시트, 토스트, 로딩 상태, 타이포그래피와 간격 등 기본 UI를 담당한다. 밑줄은 이를 기반으로 토스 안에서 자연스러운 화면과 상호작용을 제공한다.

앱인토스 WebView SDK는 토스 로그인, 앱 내 내비게이션 등 토스 앱 환경과의 연결을 담당한다. 밑줄 고유 UI는 TDS 위에 별도 컴포넌트로 구현한다.

- 실시간 가격과 등락 표시
- 종목 차트
- 매수·매도 입력과 체결 결과
- lot별 보유·매도 카드
- 거래 근거와 AI 리뷰 카드

## Zustand의 책임 범위

Zustand는 화면이 즉시 반응해야 하는 클라이언트 상태를 관리한다.

- 현재 선택한 종목과 화면 상태
- 바텀시트·모달·토스트의 열림 상태
- 매수·매도 입력값과 요청 진행 상태
- 화면에 표시할 최신 시세 스냅샷

잔액, 보유 lot, 주문 내역, 거래 리뷰처럼 정확성이 필요한 데이터는 Zustand가 진실의 원천이 아니다. 이 데이터의 진실은 백엔드와 PostgreSQL에 있고, 프론트엔드는 서버 응답과 SSE 이벤트를 반영한다. 매수·매도 성공 여부도 서버가 확정한 결과를 기준으로 표시한다.

## fetch 기반 API 래퍼

초기 HTTP 통신은 브라우저 표준 `fetch`를 감싼 작은 API 래퍼로 구현한다.

```text
api.getPortfolio()
api.createSimulatedOrder()
api.getStockSnapshot()
```

현재 필요한 것은 공통 API 주소, 세션 헤더, 오류 형식 처리, 요청 취소와 타임아웃 정도이며 `fetch`와 `AbortController`로 처리할 수 있다. 별도 라이브러리를 도입하지 않아도 요청 흐름이 충분히 명확하다.

Axios는 지금 도입하지 않는다. 인증 갱신, 복잡한 공통 인터셉터, 재시도 정책, 여러 외부 API에 대한 공통 설정 같은 요구가 실제로 생기면 다시 검토한다.

## Zod를 사용하는 이유

TypeScript 타입은 개발 중 타입 검사를 돕지만, 브라우저에서 받은 사용자 입력이나 서버가 돌려준 JSON이 실제로 올바른지 확인하지는 못한다. Zod는 경계에서 데이터를 런타임에 검증하고, 동일한 스키마로 TypeScript 타입을 추론할 수 있다.

밑줄에서는 다음처럼 정확성이 필요한 경계에 우선 적용한다.

- 매수·매도 수량, 종목 코드, `clientOrderId` 검증
- 거래 근거 입력의 필수값·길이·형식 검증
- 체결 결과, 포트폴리오, 리뷰 API 응답 검증
- 프론트엔드와 백엔드가 공유하는 주문·lot·리뷰 데이터 구조 정의

시세처럼 매우 자주 수신하는 SSE 이벤트는 신뢰 경계와 성능을 고려해 필요한 필드만 가볍게 검증한다. 모든 틱마다 무거운 검증을 반복하는 방식은 피한다.

## 실시간 전송: SSE와 자체 웹소켓

시세와 평가손익은 주로 서버에서 앱으로 전달되는 단방향 데이터다. 초기에는 SSE를 사용한다.

```text
토스증권 시세 API
  → 밑줄 백엔드의 가격 캐시
  → SSE
  → 앱인토스 WebView
```

매수·매도 요청은 일반 HTTP `POST`로 보낸다. 체결 속도는 웹소켓 여부보다 백엔드가 토스 외부 호출을 기다리지 않고 최신 가격 캐시와 PostgreSQL 트랜잭션만으로 처리하는지에 달려 있다.

밑줄 자체 웹소켓은 사용자와 서버 사이에 지속적인 양방향 통신이 필요한 기능이 생길 때 추가한다.

- 실시간 커뮤니티 채팅
- 온라인 상태·프레즌스
- 공동 편집 또는 실시간 알림 상호작용

토스증권 웹소켓은 토스와 밑줄 백엔드 사이에서 시세를 수신하는 외부 연결이다. 밑줄 자체 웹소켓은 사용자 앱과 밑줄 백엔드 사이의 연결이며, 두 연결의 책임과 제한은 별개다.

## 결정 범위

- 앱인토스 미니앱: React + Vite + TDS + 앱인토스 WebView SDK
- 상태 관리: Zustand는 UI·클라이언트 상태에 한정
- 서버 데이터: NestJS 백엔드와 PostgreSQL이 최종 진실
- 통신: `fetch` API 래퍼와 SSE부터 시작
- 검증: Zod 스키마를 주문·근거·서버 응답 경계에 적용
- 외부 웹: 초기에는 소개·시연 목적, 완전한 웹 서비스 수요가 생길 때 별도 인증과 프레임워크를 재검토
