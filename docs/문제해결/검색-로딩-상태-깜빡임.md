# 밑줄 — 검색 로딩 상태 깜빡임

## 문제 정의

종목 검색 기능(`apps/web/src/features/stock-search/`)의 상태 관리 설계에서 간헐적인 화면 깜빡임이 발생했다.

재현 절차는 다음과 같다.

1. 사용자가 한글로 "삼"까지 입력(1글자)하면, `SearchHint` 컴포넌트가 정상적으로 "검색어는 최소 2글자를 적어주세요" 안내 문구를 보여준다.
2. 이어서 한 글자를 더 입력해 "삼ㅅ"(2글자)이 되는 순간, 최소 글자 수 조건을 충족했으므로 실제 검색이 시작되어야 한다.
3. 그런데 실제 검색/로딩 상태로 전환되기 **직전의 아주 짧은 한 프레임 동안**, 마치 검색 결과가 이미 도착해서 아무것도 없었던 것처럼 "검색 결과가 없습니다" 문구가 잘못 표시됐다가, 곧바로 정상적인 로딩 → 결과 표시 흐름으로 안착한다.

데이터가 틀리게 조회되는 문제가 아니라, **순수하게 UI/상태 타이밍 버그**다.

## 원인

`useStockSearch` 훅(`apps/web/src/features/stock-search/hooks/useStockSearch.ts`)은 원래 `isLoading`을 `useState`로 관리하고, `query`가 바뀔 때 실행되는 `useEffect` 안에서 이 값을 `true`로 바꾸는 구조였다.

문제는 React의 렌더링 사이클이 **Trigger → Render → Commit** 순서로 진행되고, `useEffect` 콜백은 커밋(그리고 브라우저 페인트) 이후, **다음 틱에** 실행된다는 데 있다. 이는 React 공식 문서 "Render and Commit"(https://react.dev/learn/render-and-commit)에 명시된 내용이다.

즉, `query`가 "삼"에서 "삼ㅅ"으로 바뀌는 순간 React는 먼저 **새 query prop과 이전 state(`isLoading: false`, `stocks: []`)** 조합으로 한 번 리렌더링을 수행한다. `isLoading`을 `true`로 바꿔줄 effect는 아직 실행되지 않은 시점이기 때문이다. 이 한 프레임 동안 컴포넌트 로직은 다음 세 조건을 동시에 관찰하게 된다.

- query 길이가 2 이상 → "더 입력하라"는 가드는 통과
- `isLoading`이 `false`
- `stocks.length === 0`

이 조합은 "검색이 끝났는데 결과가 없다"는 뜻으로 잘못 해석되어, 실제로는 검색이 시작조차 하지 않은 순간에 빈 결과 화면을 잠깐 그리게 된다. 그 직후 effect가 실행되어 `isLoading`이 `true`로 바뀌면서 정상 흐름으로 복귀한다.

한 문장으로 정리하면 다음과 같다.

**파생 가능한 UI 상태(`isLoading`)를 effect를 통해 비동기적으로 계산했기 때문에, prop(`query`)과 state(`isLoading`/`stocks`)가 한 프레임 동안 서로 어긋나는 창(window)이 생긴 것이 근본 원인이다.**

## 참고한 문서

- React 공식 문서 "Render and Commit": https://react.dev/learn/render-and-commit — 렌더링이 Trigger → Render → Commit 순서로 진행되고, effect는 커밋(그리고 브라우저 페인트) 이후에 실행된다는 것을 설명함. 이 문서를 통해 "useEffect가 항상 한 박자 늦게 실행된다"는 정확한 메커니즘을 확인함.
- React 공식 문서 "You Might Not Need an Effect": https://react.dev/learn/you-might-not-need-an-effect — 다른 state로부터 계산 가능한 값은 별도 state+effect로 관리하지 말고 렌더링 중에 직접 파생(derive)해서 계산하라는 원칙. 이 문서의 원칙을 그대로 적용해서 해결함.
- 참고로, MDN Web Docs는 React 같은 서드파티 라이브러리를 다루는 곳이 아니라 HTML/CSS/JS 웹 표준 자체를 문서화하는 곳이라, 이 문제와 관련된 내용은 없다는 점도 확인함. 이 이슈는 순수하게 React의 렌더/커밋/이펙트 흐름에 관한 것이라 react.dev 공식 문서만 참고 자료로 사용했다.

## 해결 방법

`isLoading`을 effect가 갱신해주는 `useState` 값으로 두지 않는다. 대신 state에는 **`resolvedQuery: string`**, 즉 "현재 들고 있는 `stocks`/`error`가 실제로 유효한 정규화된 쿼리 문자열"만 저장한다. 이 값은 이전과 마찬가지로 effect 안에서 fetch가 실제로 완료되었을 때 한 번 설정된다.

그리고 매 렌더링마다 `isLoading`을 **동기적으로 계산**한다. 계산 방법은 단순히 `query.trim() !== state.resolvedQuery` 비교다. 두 값이 다르다면, 새 `query` prop을 받은 바로 그 렌더링 안에서 즉시 "지금 들고 있는 `stocks`/`error`는 이미 낡은 값이고 검색이 사실상 진행 중"이라는 것을 알 수 있다. effect가 뒤늦게 알려줄 때까지 기다릴 필요가 없다.

### 수정 전 (버그 있는 버전)

```ts
import { useEffect, useState } from "react";
import type { KRXStock } from "@underscore/shared";
import { searchStocks } from "../api/stock-api";

type StockSearchState = {
  stocks: KRXStock[];
  isLoading: boolean;
  error: string | null;
};

const DEBOUNCE_MS = 300;
export const MIN_QUERY_LENGTH = 2;

export function useStockSearch(query: string): StockSearchState {
  const [state, setState] = useState<StockSearchState>({
    stocks: [],
    isLoading: false,
    error: null,
  });

  useEffect(() => {
    const normalizedQuery = query.trim();

    if (normalizedQuery.length < MIN_QUERY_LENGTH) {
      return;
    }

    setState((current) => ({ ...current, isLoading: true, error: null }));

    const controller = new AbortController();
    const debounceTimer = window.setTimeout(async () => {
      try {
        const stocks = await searchStocks(normalizedQuery, controller.signal);
        setState({ stocks, isLoading: false, error: null });
      } catch (error) {
        if (controller.signal.aborted) return;

        setState({
          stocks: [],
          isLoading: false,
          error:
            error instanceof Error
              ? error.message
              : "알 수 없는 오류가 발생했습니다.",
        });
      }
    }, DEBOUNCE_MS);

    return () => {
      controller.abort();
      window.clearTimeout(debounceTimer);
    };
  }, [query]);

  if (query.trim().length < MIN_QUERY_LENGTH) {
    return { stocks: [], isLoading: false, error: null };
  }

  return state;
}
```

### 수정 후 (해결된 버전)

```ts
import { useEffect, useState } from "react";
import type { KRXStock } from "@underscore/shared";
import { searchStocks } from "../api/stock-api";

type StockSearchState = {
  stocks: KRXStock[];
  error: string | null;
  resolvedQuery: string;
};

type StockSearchResult = {
  stocks: KRXStock[];
  isLoading: boolean;
  error: string | null;
};

const DEBOUNCE_MS = 300;
export const MIN_QUERY_LENGTH = 2;

export function useStockSearch(query: string): StockSearchResult {
  const [state, setState] = useState<StockSearchState>({
    stocks: [],
    error: null,
    resolvedQuery: "",
  });

  useEffect(() => {
    const normalizedQuery = query.trim();

    if (normalizedQuery.length < MIN_QUERY_LENGTH) {
      return;
    }

    const controller = new AbortController();
    const debounceTimer = window.setTimeout(async () => {
      try {
        const stocks = await searchStocks(normalizedQuery, controller.signal);
        setState({ stocks, error: null, resolvedQuery: normalizedQuery });
      } catch (error) {
        if (controller.signal.aborted) return;

        setState({
          stocks: [],
          resolvedQuery: normalizedQuery,
          error:
            error instanceof Error
              ? error.message
              : "알 수 없는 오류가 발생했습니다.",
        });
      }
    }, DEBOUNCE_MS);

    return () => {
      controller.abort();
      window.clearTimeout(debounceTimer);
    };
  }, [query]);

  const normalizedQuery = query.trim();

  if (normalizedQuery.length < MIN_QUERY_LENGTH) {
    return { stocks: [], isLoading: false, error: null };
  }

  if (normalizedQuery !== state.resolvedQuery) {
    return { stocks: [], isLoading: true, error: null };
  }

  return { stocks: state.stocks, isLoading: false, error: state.error };
}
```

### 왜 이렇게 하면 해결되는가

수정 후 버전에서 `isLoading`은 더 이상 effect를 거쳐 "뒤늦게 도착하는" 정보가 아니다. 매 렌더링마다 그 순간 이미 동기적으로 사용 가능한 값들 — 방금 받은 `query` prop과 state에 저장된 `resolvedQuery` — 을 비교해서 즉석에서 새로 계산하는 **파생값(derived value)**이 됐다.

`query`가 바뀌면 React는 리렌더링을 한 번 수행하는데, 이 렌더링 안에서 이미 `normalizedQuery !== state.resolvedQuery` 비교가 참이 되어 `isLoading: true`가 반환된다. effect가 실행되기를 기다릴 필요가 전혀 없다. 따라서 "새 query는 반영됐는데 isLoading은 아직 예전 값"인 어긋난 프레임 자체가 존재할 수 없게 된다.

이는 React 공식 문서 "You Might Not Need an Effect"가 말하는 원칙 — **다른 state/prop으로부터 계산 가능한 값은 별도의 state와 effect로 동기화하지 말고, 렌더링 중에 직접 계산하라** — 을 그대로 적용한 결과다. `isLoading`은 애초에 "검색이 실행 중인가?"라는, `query`와 `resolvedQuery`만 있으면 항상 계산 가능한 값이었다. 이를 effect로 동기화되는 별도의 state로 만든 것 자체가 버그의 근본 원인이었고, 파생값으로 되돌리는 것이 곧 해결책이었다.
